# Blackout — game and engineering audit

Date: 2026-09-04. Audited commit: `40934a9` on `main`.

## Assessment

Blackout has a workable foundation for an arcade flight game: a compact Three.js application, separated systems, a procedural aircraft, streaming terrain, atmosphere, menus, and checkpoints. The main problems are correctness, feedback, and replay value. Improving graphics alone would leave unreliable terrain contact, navigation errors, fragile startup, and a very short activity without a scoring or retry loop.

Recommended direction: a focused arcade flying game built around low-altitude routes, precision flying, and scored landings. Preserve forgiving controls and quick access. Add depth through readable flight behavior and courses worth repeating. Radar, weapons, multiplayer, and a larger world are not prerequisites for this direction.

This document proposes changes; it does not implement them. No gameplay source was modified during the audit.

## Evidence and limits

- Reviewed the 30 TypeScript source modules, HTML/CSS interface, package/build configuration, and project documentation, with detailed tracing of flight, terrain, collision, missions, input, cameras, and lifecycle behavior.
- `npm run build` passed. Output JavaScript was 741.71 kB, 199.53 kB gzip; Vite reported its bundle-size warning.
- An additional `tsc --noEmit --strict --noUncheckedIndexedAccess` check passed. Those protections are not currently enabled in the committed configuration.
- Browser checks covered startup, title keyboard navigation, Play, pause/resume, queued camera input, chase/close/cockpit views, and day/night/weather presentation. The first launch failed during spawn generation; a reload succeeded. Static runway scenes later displayed approximately 60 fps. This was not an extended flight or cross-device performance benchmark.
- A temporary Node harness transpiled and exercised the actual source modules. Physics fixtures supplied vectors, controls, and a no-op mesh sync; they did not replace flight or collision logic. Terrain tests instantiated the real terrain builder without a GPU renderer.
- Fixed seeds 1–30 produced six spawn failures: **2, 11, 14, 19, 20, 24**. This is a deterministic regression sample, not an estimate of the probability of failure across random production seeds.
- Observed spawn searches took about 1.19–4.22 seconds in the local harness. Some diagnostics ran concurrently, so timing is indicative, not an isolated benchmark.
- No dependency-vulnerability audit, external asset-license review, sustained audio listening test, mobile gameplay test, or broad browser/GPU compatibility matrix was performed.

## Confirmed defects, ranked

### 1. Startup can fail behind a normal-looking title screen — critical

**Evidence:** [spawn search](/home/daniel/Documents/GitHub/Blackout/src/world/terrainSample.ts:759), [world reseed](/home/daniel/Documents/GitHub/Blackout/src/world/World.ts:102), [boot](/home/daniel/Documents/GitHub/Blackout/src/main.ts:55).

`findFlatSpawn()` can exhaust its searches and throw. `new World()` runs before Play and menu listeners are attached. The outer error handler only logs to the console, leaving visible buttons that cannot start the game. This happened on the first browser launch and reproduced with six fixed seeds.

Reset has an additional failure mode: `reseed()` changes the global seed and clears the active pad before validating the replacement. If search throws, existing terrain meshes and the new collision sampler can describe different worlds. The reset call is not caught locally.

**Change:** create and validate a candidate world before committing it; bound the search; provide a guaranteed valid fallback; expose loading, ready, and recoverable error states. Preserve the active world if replacement fails. The final search fallback also drops departure/footprint validation, so it needs the same postconditions as the main search.

**Done when:** a seed regression corpus always produces a usable spawn or a recoverable UI, and injected reset failure leaves the previous world intact.

### 2. Rendered water and collision surfaces disagree — high

**Evidence:** [rendered vertex heights](/home/daniel/Documents/GitHub/Blackout/src/world/TerrainSystem.ts:407), [ground queries](/home/daniel/Documents/GitHub/Blackout/src/world/ground.ts:11), [climate height](/home/daniel/Documents/GitHub/Blackout/src/world/terrainSample.ts:672).

The renderer forces water vertices to at most 0.35 m, while physics uses the climate height clamped only against zero. These are different surfaces despite the shared-heightfield comments. At an actual vertex in chunk `3,8`, seed 1, `(1312.5, 3412.5)`, the mesh height was **0.350 m** and physics height **61.309 m**: a **60.959 m** invisible difference.

There is also a general sampling issue: visible triangles interpolate sparsely sampled heights, while collision queries evaluate the continuous procedural function. Sharing a function does not by itself make coarse triangles and collision geometry agree.

**Change:** define explicit ground and water surfaces, normals, and surface types. Use a common sufficiently detailed contact representation near the aircraft; bound interpolation error. Give water its own ditching/crash outcome instead of treating it as a runway.

**Done when:** sampled visible/contact heights meet an explicit tolerance near the aircraft, including water, shores, steep slopes, and chunk boundaries.

### 3. Forward terrain impacts use the old ground position — high

**Evidence:** [initial floor query](/home/daniel/Documents/GitHub/Blackout/src/aircraft/FlightModel.ts:28), [movement and clamp](/home/daniel/Documents/GitHub/Blackout/src/aircraft/FlightModel.ts:190).

`minY` is computed before moving, then reused after movement. The later collision check uses the new position, but the impact velocity has not been classified against that new surface. The anti-cliff clause therefore misses an important class of horizontal impacts.

In a seed-1 fixture, a jet moving at 400 m/s finished a 0.05-second step approximately **2.10 m below its new contact floor**, with `impactVy = 0`. Collision returned `roll`. A subsequent ground classification can then snap it upward.

**Change:** sweep the previous-to-next position against terrain, evaluate the impact point and surface normal, and retain pre-impact velocity before resolving motion. Fixed simulation steps help but do not replace swept contact.

**Done when:** ridge impacts at the maximum supported speed and every heading reliably collide without penetrating or climbing through the surface.

### 4. Landing classification ignores attitude, surface, and objects — high

**Evidence:** [collision outcomes](/home/daniel/Documents/GitHub/Blackout/src/systems/Collision.ts:15), [automatic gear](/home/daniel/Documents/GitHub/Blackout/src/aircraft/Aircraft.ts:146).

Collision is effectively an origin-height test plus vertical-speed thresholds. It does not check wing/nose contact, pitch, roll, terrain slope, water, or obstacles. A fixture with the aircraft upside down, descending at 2 m/s and moving horizontally at 40 m/s returned `landed`, even though the flight model reported it was not grounded.

Hangars, tower, and other airfield objects are visual geometry only. There is no corresponding obstacle collision path. Moderate impacts between the soft and crash thresholds silently become `roll`. A gear-up 500 m/s contact fixture also returns `roll`; automatic gear normally hides that particular state during ordinary play, but it exposes the classifier's missing conditions.

**Change:** use a small aircraft collision shape or contact-point set, local terrain normals, and simple airfield colliders. Define valid landing conditions and distinguish a hard landing, crash, rollout, and water contact. Use AGL for the airborne latch instead of the current absolute `position.y > 8` check.

**Done when:** landing/crash outcomes match what the player sees and explain why a landing failed.

### 5. The gate direction cue is mirrored — high

**Evidence:** [bearing calculation](/home/daniel/Documents/GitHub/Blackout/src/systems/Mission.ts:207), [arrow rotation](/home/daniel/Documents/GitHub/Blackout/src/ui/HUD.ts:168), [camera framing](/home/daniel/Documents/GitHub/Blackout/src/camera/CameraSystem.ts:274).

The heading convention and CSS arrow convention disagree. For a level +Z-facing aircraft, the initial gate produces a **+31.513°** clockwise arrow rotation, but projects to screen X **−0.561**, to the left. The source comments calling +X the aircraft's right side are also inconsistent with the camera-facing convention.

**Change:** establish and test one coordinate convention. Compute bearing from an explicit aircraft right/forward basis. For a marker intended to indicate an on-screen target, project through the active camera so orbit/free-look views remain meaningful.

**Done when:** left, right, ahead, behind, and above/below cues are correct in all camera modes and at rotated headings. Verify roll/attitude labels as part of the same convention cleanup; the yaw test alone is not evidence that the D key is reversed.

### 6. Terrain never changes detail after it loads — high

**Evidence:** [existing-chunk handling](/home/daniel/Documents/GitHub/Blackout/src/world/TerrainSystem.ts:203), [geometry choice](/home/daniel/Documents/GitHub/Blackout/src/world/TerrainSystem.ts:384).

Distance chooses resolution, slope shading, skirts, and near material only when a chunk is created. Existing chunks are merely kept alive. A chunk initially loaded at far detail retained **36 vertices** after moving the focus directly onto it. Near terrain normally has 289 top-surface vertices plus skirts. Far tiles retain 84 m sample spacing even when directly underneath the aircraft.

This also affects future vegetation: a tile first created without props never gains them as the player approaches. Pending priorities use old distances, so the generation order can become stale while moving.

**Change:** track desired/current LOD, promote and demote with hysteresis, update queued priorities, and schedule geometry and prop changes separately. Test seams across transitions, not just at initial spawn.

**Done when:** flying several kilometres out and back preserves near-field quality, without cracks, large pops, or an expanding high-detail working set.

### 7. Low frame rates slow the simulation — high

**Evidence:** [main time step](/home/daniel/Documents/GitHub/Blackout/src/main.ts:195), [timing helper](/home/daniel/Documents/GitHub/Blackout/src/core/Time.ts:13).

There is one simulation step per rendered frame, capped at 0.05 seconds. Below 20 fps, elapsed time is discarded continuously. A ten-second fixture travelled about **2572 m at 60 fps** and **1286 m at 10 fps**. This is measurable slow motion, not just rough rendering. Render hitches also affect input response and contact behavior.

**Change:** use a fixed-step accumulator with bounded catch-up, render interpolation, and an explicit policy for long suspension. Pause on tab/focus loss instead of trying to simulate an arbitrarily long absence.

**Done when:** equivalent timestamped inputs give equivalent outcomes across normal rendering rates; overload and suspension behavior are explicit and tested.

### 8. Paused inputs leak into resumed play — medium

**Evidence:** [queued actions](/home/daniel/Documents/GitHub/Blackout/src/core/InputManager.ts:141), [action consumption](/home/daniel/Documents/GitHub/Blackout/src/main.ts:201).

The input manager receives keys while menus are open. Queues are cleared when entering pause, but not when leaving it. Browser reproduction: pause in chase view, press C, resume; the camera changes to close chase. R and N follow the same queue path, allowing a paused keypress to regenerate the world or change weather on resume.

**Change:** route input by game state and clear flight actions at state boundaries. Make menu controls independent of flight controls.

**Done when:** keys used inside menus never cause deferred flight actions, including after blur and resume.

### 9. Keyboard suppression breaks menu navigation — medium

**Evidence:** [global suppression](/home/daniel/Documents/GitHub/Blackout/src/core/suppressBrowserUi.ts:14), [input suppression](/home/daniel/Documents/GitHub/Blackout/src/core/InputManager.ts:110), [menu implementation](/home/daniel/Documents/GitHub/Blackout/src/ui/GameMenu.ts:39).

Tab and Enter are blocked globally, including on title/menu screens. Browser testing confirmed Tab did not move focus onto the title buttons. Menus do not manage initial focus, focus restoration, or modal focus. Ctrl as a primary flight key also creates avoidable browser-shortcut conflicts; the safer 1/2 alternatives exist but are absent from the in-game controls table.

**Change:** capture only relevant gameplay keys while flight owns focus. Support normal button activation and keyboard menu navigation, then add remapping and saveable preferences. Keep fullscreen optional and release keyboard capture at appropriate state boundaries.

### 10. Retry and mission lifecycle are incomplete — medium

**Evidence:** [quit-to-title reset](/home/daniel/Documents/GitHub/Blackout/src/main.ts:99), [new-world reset](/home/daniel/Documents/GitHub/Blackout/src/main.ts:204), [mission start](/home/daniel/Documents/GitHub/Blackout/src/systems/Mission.ts:99).

Quit to title resets the aircraft but not mission progress. Play can restart the aircraft with an already advanced or completed circuit. R regenerates terrain, weather, spawn, and gates together. There is no same-course retry, return-to-runway action distinct from world generation, or explicit post-completion flow.

**Change:** separate Retry flight, Restart challenge, and New world. Introduce explicit session states and a course definition that survives retries. Reset mission state intentionally rather than as a side effect of world generation.

### 11. Gates test a proximity slab, not a real crossing — medium

**Evidence:** [gate detection](/home/daniel/Documents/GitHub/Blackout/src/systems/Mission.ts:157).

The `inside` branch accepts proximity on either side of the gate plane. Placing the fixture 10 m beyond the first gate, without a previous crossing, immediately returned `pass`. The crossing branch tests radial distance at the frame endpoint rather than at the actual plane intersection, which can misclassify diagonal edge crossings.

**Change:** intersect the motion segment with the gate plane and test radius at that intersection. Specify whether reverse passes count. Resolve collision before awarding progress when both happen in the same step.

### 12. Pause does not freeze challenge conditions — medium

**Evidence:** [world update outside play gate](/home/daniel/Documents/GitHub/Blackout/src/main.ts:252), [weather/time update](/home/daniel/Documents/GitHub/Blackout/src/world/Atmosphere.ts:472).

Weather, daylight, crash effects, and camera animation continue while paused. The browser showed the clock advancing from dusk into night while the pause menu remained open. The app clears held keys on blur, but does not pause flight. Wall-clock banners can also expire while paused.

**Change:** separate simulation time from optional cosmetic menu animation. Freeze conditions for scored challenges and pause on lost visibility/focus. Free-flight background ambience can be an intentional separate policy.

### 13. Afterburner has three different activation rules — medium

**Evidence:** [flight thrust target](/home/daniel/Documents/GitHub/Blackout/src/aircraft/FlightModel.ts:95), [plume](/home/daniel/Documents/GitHub/Blackout/src/aircraft/Aircraft.ts:170), [audio](/home/daniel/Documents/GitHub/Blackout/src/audio/FlightAudio.ts:59).

Physics applies boost regardless of throttle; the plume requires throttle over 5%; audio requires over 2%. At zero throttle the physics fixture accelerated under boost while those boost feedback paths were disabled. HUD displays 100% while boosting, obscuring the retained lever setting and the speed target that returns on release.

**Change:** derive one engine state with lever, effective power, afterburner state, and target/output values, then share it with physics, sound, and HUD.

## Design changes with the highest payoff

These are product judgments, not all correctness defects.

### Give the player something worth repeating

The current five-gate circuit has no timer, score, medal, best run, ghost, difficulty ladder, or landing objective. Completion is primarily a banner and a changed label. R removes the course the player was learning.

Build a short, reliable sequence: start briefing → takeoff → timed route → scored landing → results → instant same-course retry. Use gate accuracy, elapsed time, and landing quality as understandable metrics. Save best results per course/seed locally. Start with a few carefully designed courses before expanding procedural challenge variety.

Potential later variants: low-altitude navigation, precision gate slalom, approach-and-landing trials, and free flight with discoverable landmarks. A restrained G-load/blackout mechanic could fit the title, but should follow reliable handling and clear warning feedback.

### Tune flight around readable consequences

The present model deliberately treats ENG% as a speed command and aligns velocity to the nose. That is a legitimate arcade choice. Its limitation is that acceleration, deceleration, turning, and climbing have little sustained energy tradeoff. Throttle reduction acts as automatic braking; roll alone has no coordinated bank-turn assistance. The model has no meaningful load-factor feedback.

Retain an assisted mode, make speed hold explicit, and tune a small set of understandable properties: acceleration, turn authority, energy loss in hard manoeuvres, climb performance, braking, low-speed recovery, and takeoff/landing envelopes. Offer familiar roll-on-A/D and rudder-on-Q/E as a configurable preset, while retaining the current scheme as an option.

The measured zero-to-full throttle hold takes approximately **12.62 seconds**. That helps fine adjustment but makes large corrections slow. Combine faster coarse control with fine trim or discrete target settings. Afterburner increases top speed only about 4% over dry maximum, although it materially raises acceleration and overrides lower speed targets; tune and communicate its role deliberately.

Do not mistake unused configuration for implemented physics: mass/thrust, parasite drag, airbrake, and wheel-brake settings are not consumed by the current flight calculations.

### Generate flyable routes, not just safe gate centres

Gate altitude is checked at each gate, not along the route. In seed 1, the straight segment from gates 2 to 3 passed **431.38 m below terrain**. Seed 4 also had a terrain-intersecting direct segment. These tests do not prove the courses are impossible: a player can climb or detour. They do show that the guidance does not supply a validated clear route.

The first ring is tangent to a circle centred on the spawn, so it is edge-on when approached directly from that centre. A beginner-friendly first gate should align with the takeoff path. Subsequent placement should respect a chosen speed, turn radius, climb envelope, approach heading, and terrain clearance. Guide players through the intended path and validate the whole corridor.

### Make the world useful to flight

Vegetation is completely disabled. Much of the biome distinction is terrain shape and vertex color. The browser views showed broad bare surfaces, limited close-range scale cues, and very dark terrain at night. Infinite area has little value without recognizable destinations or routes.

Prioritize a coherent visual style, strong terrain silhouettes, readable surface detail, forests in clusters, a few memorable structures, and landmarks useful for navigation. Fix LOD first. When restoring vegetation, replace the hard-coded exclusion around world origin with the actual translated/rotated airfield footprint. Simply toggling the flag would retain both the LOD/prop-update bug and misplaced runway exclusions.

Water currently uses the same terrain-material pipeline. Give water a deliberate surface appearance and shoreline treatment after fixing its contact rules. Rain/snow are square point particles; cloud formations are many transparent low-poly meshes. Improve their readability and cost together instead of merely increasing counts.

### Improve cameras and information hierarchy

Cockpit mode hides the entire aircraft; it is a first-person camera without a visible cockpit or look-around. Build a lightweight cockpit frame and mode-specific HUD, or label the current mode accordingly. External cameras should keep the horizon readable through loops. Heading from `atan2(forward.x, forward.z)` becomes unstable near a vertical nose and changes by roughly 180° across the top of a loop.

Camera ground avoidance samples a floor at the endpoint, not the full sightline, and does not handle buildings. Use a short collision sweep or sampled obstruction path between the aircraft and desired camera. Allow camera shake, speed FOV, sensitivity, and auto-return to be adjusted.

Move essential flight and target information toward the player's visual focus: path/aim reference, correct gate marker, speed/target speed, vertical speed, clearance, and landing cues. Put FPS and secondary environment labels behind a diagnostic/minimal-HUD setting. The current HUD uses numerous corner panels and offers no in-flight onboarding.

All warning outputs are disabled: stall and low-altitude flags are false, and gear warning is permanently false. Replace them with tuned, contextual warnings, especially terrain closure and unsafe approach, rather than merely enabling noisy thresholds.

### Make sound explain events

The current audio supplies engine and wind loops only. Crash, checkpoint, completion, and touchdown have no event-sound implementation. Add those events, plus useful warning tones and subtle control/gear feedback. Supply master/engine/wind/effects volume controls and persist them. The audit established audio routing from code; it did not assess perceived mix quality by listening.

## Performance and maintainability

1. **Measure streaming time, not fictional cost units.** `BUILD_BUDGET = 2.4` is an estimated work score, not milliseconds. Local CPU-only terrain runs reached about 26.45 ms at the 95th percentile and 144.88 ms maximum for initial updates under mixed machine load. Use elapsed-time budgets, cancellable jobs, and worker generation where measurements justify it. Keep the simulation responsive while loading.
2. **Reduce hot-path terrain work.** Even a ground-height lookup invokes the complete climate pipeline, including four neighbour height evaluations. Aircraft, collision, camera, effects, and debug repeat queries. Separate the minimum contact query from presentation fields and cache appropriate samples within a simulation step.
3. **Manage draw calls and materials.** A settled stream contains about 1,313 chunks in the tested configuration. Each visible chunk has its own mesh and cloned material; clouds add many separate meshes. Resident count is not the number drawn each frame. Add renderer statistics and CPU/GPU timing before choosing batching, shared materials, instancing, or a smaller visibility radius.
4. **Provide quality controls.** Antialiasing, shadows, view distance, and resolution policy are currently fixed. Add presets and resolution scaling; test low-end hardware before claiming a target frame rate.
5. **Unify sky output processing.** The custom sky writes raw fragment color without the tone-mapping/output-color chunks used by the installed Three.js standard/background shaders. Align the output pipeline so sky and fog can be tuned consistently. Runtime also reported deprecated `PCFSoftShadowMap`, with Three.js falling back to `PCFShadowMap`.
6. **Make runtime contracts explicit.** Use a session controller and immutable world/course definitions. Keep mutable seed/pad data in a world instance, rather than module globals. Emit events for impacts, gates, completion, and resets, then let UI/audio/effects consume them. A large ECS rewrite is unnecessary at this scale.
7. **Add focused regression coverage and CI.** No test suite or CI configuration was found. Begin with the failures in this report, plus seed validation, contact normals, gate crossing, and state transitions. Enable strict TypeScript checks, which already pass. Check the build and these regressions on each change.
8. **Clean up asset and lifecycle contracts.** The optional GLB path assumes scale/orientation/node naming without a declared model contract, shifts the imported bottom to local Y=0 despite aircraft-origin clearance, and removes the placeholder without disposing its resources. Those are latent import-path issues; no GLB is bundled. Cache mesh references instead of searching/traversing the aircraft multiple times per frame. Add teardown where sessions can be reconstructed.
9. **Update documentation to match shipped behavior.** Vegetation and warnings are disabled. Several tuning fields and fullscreen helper paths are unused. State the supported desktop keyboard experience and document actual controls; narrow-screen CSS alone does not provide touch gameplay.

## Recommended delivery order

| Stage | Deliverable | Completion criteria |
|---|---|---|
| 1. Reliable session | Safe startup/reseed, common surfaces, swept contacts, obstacle/landing rules, correct nav, input isolation, fixed simulation time | Seed corpus and fault injection pass; ridge/water/inverted-contact regressions pass; menus and guidance behave correctly |
| 2. Repeatable challenge | Explicit course/session state, same-course retry, timer, accuracy/landing score, results and saved bests, clear daylight introduction | A player can complete a short route, understand the result, and retry the identical challenge immediately |
| 3. Flight feel and feedback | Tuned assist/energy behavior, configurable controls, unified engine state, camera improvements, warnings and event sounds | Representative players can take off, turn, recover, navigate, and land without unexplained failures; handling remains stable across render rates |
| 4. World and rendering | Dynamic LOD, generation budgets/workers as needed, quality presets, vegetation, landmarks, water and atmosphere polish | Stable near-field detail during travel; measured frame-time targets on a declared hardware tier; readable flight in every supported condition |
| 5. Content expansion | More authored/procedural courses, route validation, ghost replay and optional advanced flight challenges | New courses satisfy clearance/turn/climb constraints and reuse the established scoring/retry loop |

A useful first vertical slice is one reliable daytime airfield, one teachable route, a satisfying landing, and an instant scored retry. It establishes the experience that all later terrain and content work must improve.
